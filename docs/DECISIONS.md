# Decisions

| Date | Decision | Why |
| --- | --- | --- |
| 2026-11-08 | Sell first to DPO consultancies, not single organisations | One sale brings many client organisations; per-client pricing fits their retainers |
| 2026-11-08 | Deadline rules follow ICO guidance, tested against its worked examples | A wrong date is the product's worst failure |
| 2026-11-08 | AI never acts alone: a person confirms triage and sends letters | Keeps responsibility with the controller; limits harm from a misread |
| 2026-11-08 | Postgres with row-level security as the isolation boundary | Isolation must not depend on app code being perfect |
| 2026-11-08 | Next.js + Supabase + shadcn/ui | Largest ecosystem, best AI tooling support, hosted Postgres with auth and RLS in one service |
| 2026-11-08 | The Data API grants reach the signed-in role only; the anonymous role gets nothing in `pd` | The public form (slice 5) will write through a server route, so nothing needs anonymous table access; Supabase's standard grants would open every table to it |
| 2026-11-08 | Next.js Cache Components switched off for now | Every page is per-user, so there is nothing to prerender yet, and with it on each session read needs its own Suspense boundary. Revisit when a public page is worth caching |
| 2026-11-08 | A new user creates their consultancy through `pd.create_partner`, a definer-rights function, and becomes its admin | `partners` has no insert policy and a membership can only be added by an existing admin, so nothing else could bootstrap the first user |
| 2026-11-08 | Partner admins must enrol an authenticator app; the app sends them to enrol or to enter a code before the desk | Admins can read every client's data. Enforcement in the database itself (an `aal2` check in the policies) joins the slice 7 checklist |
| 2026-11-08 | Every case action is one database function call (`pd.record_case_action`) that changes the case and writes its audit event in the same transaction | Two statements from the app could leave a change without its event. The function also refuses impossible actions, so the rules live in one place |
| 2026-11-08 | Case references are `<client code>-<number>`, numbered per client and never reused | Short enough to quote on the phone; the client code makes the owner obvious in a mixed list |
| 2026-11-08 | Action dates may not be in the future | A deadline worked out from a future date would be fiction; backdating is allowed because requests are often logged late |
| 2026-11-08 | Inbound email is keyed by a per-client token in the forwarding address, through definer-rights functions the anonymous role may call | The app then needs no service key anywhere. The anonymous role has usage on the `pd` schema so those functions resolve, but no table grants |
| 2026-11-08 | Triage uses Claude Opus 5.5 at low effort with a fixed JSON schema; the keyword check runs when a client has AI off, no key is set, or the call fails | The screen always says which one spoke. A person confirms every result and the audit event records both |
| 2026-11-08 | Letter drafts are copied, never sent | The app never sends email on its own (CLAUDE.md). The person sends from their own mailbox |
| 2026-11-08 | Client codes are unique across every consultancy, not just within one | The public form lives at `/r/<code>`, so a code has to name one client. Case references were already unique across the whole table, so this only made an existing assumption explicit |
| 2026-11-08 | The public form writes through definer-rights functions keyed by the client code and a hashed one-time token; the submissions table has no grants for any app role | Nothing a visitor can reach needs a session or a table grant, and a copy of the table cannot be used to verify someone else's request |
| 2026-11-08 | A web form request is received on the day the link is opened, not the day the form was filled in | The design standard: the clock starts when the request is complete, and an unverified address is not a complete request. Unverified submissions are deleted a week after the link expires |
| 2026-11-08 | The app sends two transactional emails for the public form (the link and the confirmation), through Resend | These are messages the requester asked for by filling in the form. "The app never sends email on its own" in CLAUDE.md means case correspondence: letters are still drafted, copied and sent by a person |
| 2026-11-08 | The confirmation states a legal response date based on the requester's own choice of type, before a person has triaged it | A requester expects to be told when to expect an answer (design standard §6). The sentence says the time runs later if identity has to be checked, and the consultancy confirms the date in its own acknowledgement. Revisit if pilots find the date causes disputes |
| 2026-11-08 | Web form requests get their own reference (`<code>-W0001`) that the case keeps as `source_ref` | Cases are numbered only when a person accepts the item, so the requester cannot be given the case reference on the spot. The case page and search both know the web reference |
| 2026-11-08 | The service role is used in one place only: the nightly job route, server-side, behind `JOBS_SECRET`, with explicit grants for just what the job does | Reminders have to see every consultancy's cases and read members' email addresses, which no user session can. Nothing else in the app has that key, and the browser never does |
| 2026-11-08 | Reminder digests are internal email to the consultancy's own staff, one per person per night | They are not case correspondence, so they sit outside the "never sends letters" rule, like the public form's emails. The digest says nothing has been sent to the requester |
| 2026-11-08 | The monthly report PDF is rendered on the server with @react-pdf/renderer, from the same text as the page | No browser needed on the server; one page, the client's name and colour, same words as the page so the two never disagree |
| 2026-11-08 | Bank holidays for all three regions come from the GOV.UK feed, upserted nightly | One source for the dates, and Scotland and Northern Ireland work without hand-typed lists. The engine's built-in England and Wales list is only a fallback |
| 2026-11-08 | A partner admin's membership counts in the policies only when the token says `aal2` | The app already sent admins to enrol, but a rule only the app enforces can be skipped by calling the API directly. Now the database refuses them. Other roles see one client at most and are not yet required to enrol |
| 2026-11-08 | Idle sessions end after 8 hours (`SESSION_IDLE_HOURS`), enforced by the proxy with an HTTP-only cookie | Supabase's own inactivity timeout is a Pro feature; this works on every plan and sends the person to sign-in with a sentence saying why |
| 2026-11-08 | The public form caps each sender address at ten submissions an hour, storing only a daily-salted hash of the address | Enough to stop a script filling the inbox without storing network addresses, which would themselves be personal data |
| 2026-11-08 | Legal pages are drafts written by the developer, shown with a banner until a solicitor has reviewed them | Better to have the structure and the facts (sub-processors, retention, roles) written down and visible than nothing; the banner stops anyone mistaking them for terms in force |
| 2026-11-08 | `AI_DISABLED=1` switches AI off for the whole deployment | A provider's terms or an incident can change overnight; one environment variable is faster than editing every client |
| 2026-11-11 | The audited functions are the only way to change a case, a clock pause, an audit event or an inbox item: they run with definer rights and check membership themselves, and the signed-in role has only select on those tables (migration 0009) | A review found that anyone with write access could update a case through the Data API with no audit event. A rule the database enforces cannot be skipped by calling the API directly |
| 2026-11-11 | The public form's database functions need a server key (`FORM_SERVER_KEY`); the database holds only its hash (migration 0010) | The anonymous role could call them with the publishable key and choose its own token, so a request could be marked "email address verified" without an email being opened. A key only the server holds closes that without giving the form the service role, which stays with the nightly job |
| 2026-11-11 | Retention covers the inbox: an item is deleted with its case, and a declined item once it is older than the client's retention period (migration 0011) | Message bodies were kept indefinitely, and the retention run failed outright on any case that had come from the inbox |
| 2026-11-11 | A reminder is a stage a case has reached (within 7 days, within 2, due today, overdue), owed to each person until the log says they were sent it for that due date; the log is written only after the email went, and the job answers 500 if anything failed (migration 0012) | Reminders used to fire only on the exact day and were logged even when the send failed, so one bad night lost a reminder for good. Nothing was sent once a deadline had passed |
| 2026-11-11 | "Today" is the date in London, in the database (`pd.today()`, migration 0013) and in the app (`src/lib/today.ts`) | Servers run on UTC. Between midnight and 1am in British Summer Time a UTC date is still yesterday, which put received dates and days left a day out |
| 2026-11-11 | Case and web form references are numbered from a per-client counter that only goes up (`pd.ref_counters`, migration 0014) | Numbering from the highest surviving row let retention bring an old reference back: a client with no form requests for 90 days restarted at W0001 |
| 2026-11-11 | An extension can only be recorded with a date inside the first month, as the clock stands (migration 0015) | The person must be told within one month (ICO guidance; UK GDPR Article 12(3)). Accepting any date let a case that was already late be extended afterwards and shown as on time. A late case now stays visibly late |
| 2026-11-11 | A client organisation cannot be deleted through the API; admins can only add and edit (migration 0016) | One call deleted a client with every case and audit event, leaving no record. Until there is an audited way to offboard a client, removal is done by the database owner by hand |
| 2026-11-11 | The emailed link opens a page with one button; the request is verified, and the clock starts, when the button is pressed, not when the link is opened | Mail scanners and link previews open links. With the old page that verified the address and started the legal clock without the person doing anything. This refines the 8 November decision: "the day the link is opened" is now the day the button is pressed |
| 2026-11-11 | `APP_URL` is required in production; without it the public form refuses submissions | The link in the verification email was built from the request's Host header when `APP_URL` was unset, and a sender can forge that header to have the app email someone a link to another site carrying their token |
| 2026-11-11 | The inbound email functions need a server key (`INBOUND_SERVER_KEY`) as well as the client's forwarding token (migration 0017) | The token is part of the forwarding address and travels in mail headers, so anyone who had seen an address could write to that client's inbox with the publishable key, skipping the webhook's secret. This refines the 8 November decision that the token alone is the credential |
| 2026-11-12 | Redesign: indigo is the one accent colour, on a soft grey canvas with white cards and a dark navigation rail | The first build used the component library's default greys, so nothing stood out and it read as a template. Indigo is kept apart from the four status colours (green, amber, red, blue), which still only ever mean a status |
| 2026-11-12 | Status colours are theme tokens used through one `Tag` component, not per-page colour classes | The same status was coloured by hand in six files; one component keeps tags consistent and always worded |
| 2026-11-12 | The navigation shows two counts: inbox items waiting and overdue cases | They answer "is there anything I must look at?" from any page. Both are counted through the user's own session, so row-level security decides what is counted |
| 2026-11-12 | "Log a case" and the command palette live in a bar above every page; the case page names the next step as its main button | Common jobs took a trip to the case list first, and the case page left the user to work out which step was next |
| 2026-11-12 | The navigation is a bar across the top, not a side rail, and every signed-in page uses the full width | Asked for after the first redesign: content sat in a narrow column with empty space either side. Five sections fit a top bar, which gives the whole width to tables and side-by-side panes. `docs/DESIGN-STANDARD.md` section 8 is updated to match |
| 2026-11-12 | The case list is a dense table grouped by urgency (Overdue, Due within 5 days, On track, Clock not running, Acknowledged, Closed), with a preview panel beside it | Patterns taken from enterprise table guidance and Linear: pinned headings, grouping with headings that stay in view, and "find, decide, act" without leaving the list. The groups follow the existing deadline sort, so no date rule changed |
| 2026-11-12 | Table column headings sort the table (cases, and the dashboard's by-client table); the sort is kept in the page address | Asked for after the full-width redesign. Sorting by a column replaces the urgency groups with one flat list; a third click returns to the grouped deadline order. Filters stay in the bar above the table |
| 2026-11-12 | Several saved emails (.eml, or Outlook .msg) can be imported into the inbox at once, read in the browser | Requests often sit in the consultant's own mailbox, and pasting them one by one is slow. Reading the file in the browser means the file and its attachments never leave the computer: only sender, subject, date and text are stored |
| 2026-11-12 | An imported email keeps the date it arrived and its own id (migration 0018) | The clock runs from the day the email arrived, not the day it was imported, so the accept form must start from the real date. The id stops the same email becoming two inbox items. A future date is refused |
| 2026-11-12 | The dashboard is a live operations view: a live queue, a due calendar, a client board and work by type, refreshed every five minutes, with every number opening the cases behind it | Modelled on the layout of a live case-management dashboard the owner uses at work (sections and the questions they answer only; no data, queries, wording or branding were taken from it). It answers "what needs doing now and where" rather than only "how many" |
| 2026-11-12 | The dashboard groups open cases by client where the reference dashboard groups by person | Cases here have no owner, so there is nothing to group by person. Client is the unit a consultancy answers to |
| 2026-11-12 | "Since your last visit" on the dashboard is kept in the browser only | It needs no record on the server of who looked at what and when, and it is one person's convenience, not case data |
| 2026-11-12 | Look-and-feel preferences (theme, table density, navigation position, preview position, how cases open, visible columns) are kept in a cookie in the person's browser | They are conveniences, not case data. A cookie lets the server draw the page right first time with no flash and no database table; the cost is that they do not follow the person to another computer. Light is the default, so the look only changes when someone chooses it |
| 2026-11-12 | A display name is kept in the person's own sign-in record, not in the case data | It needs no database change and is only shown to that person. The audit trail still identifies people by account |
| 2026-11-12 | Saved case-list views are stored in the database, private to each person (migration 0019) | Unlike the look, a named view is something people build up and expect to find again on any computer. A view stores only filter choices, never case data |
| 2026-11-12 | An inbox decision can be undone, and nothing is deleted by it (migration 0019) | A declined message can go back to the inbox; a case made from a message can be returned there to be triaged again. The case is closed, keeps its reference and trail, and is marked as returned; every decision and undo is written to an append-only inbox log |
| 2026-11-12 | A case returned to the inbox is left out of the on-time figures, the dashboard counts and the monthly report | The request is counted under the case it becomes when the message is accepted again; counting both would double it. No deadline is worked out differently |
| 2026-11-12 | A letter draft can be opened in the person's own email program, with the recipient, a subject, the reply and the original message underneath | Asked for: copying a draft into an email by hand was slow. It is an ordinary email link, so the app still sends nothing; the person reads it in their own program and presses send. This keeps the rule that a person sends every letter |
| 2026-11-12 | The subject line is built by the app, not written by AI: "Re:" plus the person's own subject when they gave one, otherwise what the letter is, always with the case reference | A reply that keeps the original subject threads with the person's email, and a reference in every subject makes later mail easy to match to its case. Built from case facts, it cannot be wrong in the way a generated one could |
| 2026-11-12 | Drafts are signed with the sender's own name and job title from their profile, then the client's name; gaps in square brackets when the profile has none | Asked for. The name and job title live in the person's sign-in record, like the display name, so no database change is needed |
| 2026-11-12 | The app checks every draft against the case and highlights what to complete or verify: gaps in square brackets, dates that are not dates of the case or whose weekday is wrong, a reference that is nearly this case's, and a title such as "Ms" the case never gave | Asked for. An AI draft can state a wrong date or guess how to address someone; these are checked against facts the app already holds, in the browser, with no further AI call. The AI is also told not to guess a title |
| 2026-11-12 | Email links are kept under 2,000 characters on Windows (7,000 elsewhere); what does not fit goes on the clipboard, the original message first | On Windows a browser silently ignores a longer email link. The reply is handed over first; if the original message does not fit it is put on the clipboard to paste underneath, and only a very long reply falls back to pasting everything |
| 2026-11-12 | A sent email can be dropped onto a step (acknowledge, ask for ID, ask for clarification, extend, close) and the app keeps a short record of it, not the email | Asked for. The record is when it was sent, who it went to and whether that is the address on the case, the subject, the attachment names and a one-line summary; it goes on the same audit entry as the step (migration 0021). The step is dated by the day the email was sent, which is more accurate than typing a date |
| 2026-11-12 | The sent email is read in the browser and never uploaded; only the text of the reply goes to the server, and only for the summary | Data minimisation: the audit trail should show that a reply went and to whom, not hold a second copy of personal data. Attachments are named, never opened or stored |
| 2026-11-12 | The summary of a sent email is written by AI only when the client's AI switch is on; otherwise it is the first sentence or two of the email. Either way the person can change it before it is recorded | The same rule as triage and letters: with the switch off, nothing about the case reaches the AI provider. The AI is told not to include names or other personal details |
| 2026-11-12 | An email that did not go to the address on the case is flagged in red but can still be recorded; the person's own email dropped by mistake is refused | People have more than one address, so a mismatch is the person's call and is written into the record. An email from the person is not evidence of anything sent to them |
| 2026-11-12 | On a case, the details and the request as received sit in the top pane under the due date; the column beside the page holds only the box for recording a step or a note, and the audit trail | Asked for. Who it is from and what they asked for are read together with the deadline, and the side column is left clear for recording what was done and seeing what has been done. The pane arranges itself by its own width (two columns, or one when narrow), so it behaves the same with the navigation on top or at the side |
| 2026-11-12 | The details and the request as received start closed on every case, showing only their two headings with arrows; either heading opens or closes both. Opened, a long request is cut to eight lines with "Show all of it" | Asked for. Closed, the due date and the steps have the screen; the client and the person's name are already in the page heading. The row opens as one because it was asked for as one section, and a half-open row reads oddly |
| 2026-11-12 | A letter draft can be stopped while it is being written, or discarded afterwards; the last discarded draft can be put back until another letter is chosen | Asked for. A draft that is not wanted should not have to sit on the page. Discarding is one click with no "are you sure", so the draft can be put back in case it had been edited. A draft stopped part way is not kept |
| 2026-11-12 | Stopping a draft, or leaving the page while one is being written, also ends the request to the AI provider | Otherwise the letter is written to the end, and paid for, with nobody reading it |
| 2026-11-13 | The subject line an email or web form arrived under is shown with the request on a case and in the preview, and as a Subject column in the cases table that can be sorted, searched and hidden | Asked for. The summary says what the request is about but does not help find the original email in a mailbox; the subject does, and it can be copied to search for. It is read from the inbox message the case was made from, which is already kept for as long as the case, so nothing new is stored and no migration was needed |
| 2026-11-13 | A column added to the cases table shows for people who chose their columns before it existed. Saved column lists, in the browser and in saved views, now carry a version | A saved list from before a column existed says nothing about that column. Without this, Subject would have stayed hidden for anyone who had ever changed a preference. Once someone hides it, it stays hidden |

## Open questions

- Working name "Privacy Desk": check Companies House and the UK IPO trade mark register before branding.
- Reminder recipients: every member who can see the case gets the digest, with no per-person switch. Add one in settings once someone asks for it.
- Second factor for client users and read-only users: today only partner admins must enrol. Decide before the first client organisation gets its own sign-in.
- Content security policy: inline scripts and styles are allowed because Next emits them. Move to a nonce-based policy once the app is deployed and the exact script set is known.
- The case page's "no bank holidays loaded for Scotland yet" notice disappears once the nightly job has run. Until the job is scheduled, run it by hand after creating the project (see `apps/web/README.md`).
- Should complaint outcomes have an internal target per client (default 28 days) or a fixed one? Ask the first pilots.
- Inbound email domain: forwarding addresses need a domain whose MX records point at Postmark (or Resend inbound). Which domain, and who owns the Postmark account? Until then the client page shows the address without a domain.
- AI provider terms: requester messages go to Anthropic for triage and drafting. The slice 7 checklist needs the data processing agreement and no-training terms confirmed before any real data; the per-client switch already exists.
- Display names: the audit trail can only say "you" or a shortened user id, because nothing stores a person's name. A small profiles table (user id, name) filled at first sign-in would fix it. Which slice?
- Inviting colleagues: the first user is the consultancy's only member. Adding a second admin or a client user needs an invitation flow (email, accept, membership row). Which slice, and should client users sign in at all in the first version?
- Supabase's built-in email sender allows only a few messages an hour, which limits sign-in testing. The app now has a Resend sender for the public form (slice 5); point Supabase Auth's SMTP settings at the same Resend account before pilots so sign-in links go the same way.
- Rate limits on the public form: today there is a honeypot field, a 24-hour token and a cap of five submissions an hour per email address and client. Per-IP limits and a bot check belong to the slice 7 checklist.
- Default privileges from migration 0002 hand every new table to the signed-in role. Migration 0006 revokes them for `form_submissions`; any future table that no app role should read needs the same line. Consider dropping the default privileges and granting per table instead.
- Two copies of the deadline rules now exist: `packages/clocks/clocks.js` (JS, 14 tests) and `apps/web/src/lib/clocks.ts` (TypeScript, same tests plus typing). CLAUDE.md names the package as the single source of truth. Proposal: once slice 3 ships, make the TypeScript module the source and either retire `packages/clocks/` or turn it into a workspace package the app imports. Until then, change both and run both test suites.
- Declined inbox items are kept for the client's full retention period, the same as closed cases. A declined message is often not a data protection matter at all, so a shorter period (for example 6 months) may be more proportionate. Ask the first pilots.
- Overdue cases appear in the reminder digest every night until they are closed. Right for a missed legal deadline, but ask the first pilots whether nightly is too often.
- Offboarding a client: when a consultancy stops acting for a client, its cases should be exported or handed back and then deleted, with a record that this happened and who asked. Today only the database owner can remove a client (migration 0016). Design this before the first client leaves.
- Redesign (12 November 2026): the dark theme has matching colours but nothing switches it on. Should the app follow the device setting, offer a switch, or stay light only?
- Case list (12 November 2026): rows are a fixed compact height and columns cannot be sorted, hidden or resized. Table guidance suggests a density switch and sortable columns; add them when a pilot user asks, and decide then whether the choice is remembered per person.
- Email import (12 November 2026): at most 25 emails at a time, attachments are ignored, and a mailbox cannot be connected directly. Connecting Outlook or Gmail (Microsoft Graph or the Gmail API) would remove the save-and-drop step, but it means holding access to a whole mailbox, which is a much bigger security and consent question. Decide after pilots say how they receive requests.
- Email import: Outlook .msg files are read by a library but have only been tested with .eml files so far. Try real .msg files dragged from classic Outlook before relying on it.
- Dashboard (12 November 2026): there is no board by person because cases have no owner. If consultancies want to see workload per team member, cases need an assignee first (who may assign, is it audited, does the reminder digest follow it?). Ask the pilots.
- Undo (12 November 2026): only an open case that came from an inbox message can be returned to the inbox. A case logged by hand has no message to go back to, and a closed case must be reopened first. Is that enough, or do pilots need to correct a hand-logged case's type or received date another way?
- Undo: a returned case cannot be reopened, because its message is live in the inbox again. If a return is itself a mistake, the message is simply accepted again as a new case with a new reference. Confirm that two references for one request is acceptable to clients.
- Preferences (12 November 2026): kept per browser. If people work across several computers and want the same look everywhere, move them into the database beside saved views.
- Letters (12 November 2026): drafts are signed with the sender's name and job title and then the client's name, as if the sender writes for the client. If a consultancy writes in its own name on a client's behalf, the sign-off needs the consultancy's name and wording such as "on behalf of". Ask the pilots how they sign.
- Letters: when a reply and the original message are too long for an email link, the rest is pasted from the clipboard. A downloadable draft file (.eml) would open complete in classic Outlook, Apple Mail and Thunderbird with no pasting; add it if pilots hit the limit often.
- Letters: opening a draft in the email program is not recorded on the case, because the app cannot know whether it was sent. The person is offered the matching step to record instead. Should opening a draft write an audit event of its own?
- Email evidence (12 November 2026): only steps where an email is sent take a dropped email. The two incoming steps (proof of identity received, clarification received) could take the person's email the same way, to date the step by when it arrived; those dates restart the legal clock, so it would help accuracy. Add it if pilots want it.
- Subject line (13 November 2026): a case logged by hand has no subject, and a case returned to the inbox loses its own (the message goes back to the inbox and takes the subject with it). Should "Log a case" take an optional subject, and should a case keep its own copy? Both need a column on the case, which is a migration.
- Case page (12 November 2026): the details and request row is closed each time a case is opened, and the choice is not remembered. Should it stay open once someone has opened it (per browser, like the other preferences), or be a setting on the profile page? Ask the pilots which they reach for more.
- Letters (12 November 2026): a draft exists only on the screen, so it is lost on leaving or reloading the page, and "Put it back" only reaches the last one discarded. Should drafts be kept with the case until they are sent or discarded? That would store draft text, which is personal data, and would need a retention rule and an audit event.
- Email evidence: the record is text on the audit entry. If reports ever need to count or filter by it (for example every reply that went to a different address), it should become structured fields.
